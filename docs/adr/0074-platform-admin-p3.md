# 0074: Platform Admin P3 operational controls and audited private files

Status: owner-authorized implementation, 2026-11-25. P2 is accepted locally and pushed as `8bfba88`. The owner subsequently authorized committing and pushing the existing P3 implementation on 2026-11-25. No deployment or P4 authorization.

The owner explicitly approves Super Admin private-file viewing/download without a case approval. This supersedes ADR 0071's original private-content default only for the separate `admin.storage.private_files.read` capability. Other roles receive no file capability. Recent persisted MFA, an exact file/physical Space/logical scope, current custody and parent availability, replay safety and scan/hash verification remain mandatory. The Admin never becomes a Planner member. Streams use fixed safe filenames, no-store/nosniff/sandbox headers and raster-only inline rendering. Every attempt and final outcome is audited; a detached opaque file ID survives source erasure. No general task/note/message search or content API is added.

Storage owns file bytes/metadata; Spaces supplies a narrow injected scope-authority function through its existing public facade. The callback checks Personal ownership metadata or current Shared activation, physical custody, logical scope, domain custody and Company ancestors. This preserves module ownership without platform imports of business internals or impersonation.

Use the existing PostgreSQL/pg-boss, storage, SMTP/sink and Admin command/audit boundaries. Health reports actual per-process request/error/latency/throughput measurements, bounded dependency probes and durable worker heartbeat. Measurements identify their instance and process lifetime; no synthetic distributed metrics. Error alerts use a five-minute window. Operational incidents retain start/recovery, safe causes, audited actions and immutable operator notes. Rules configure thresholds, severity, in-app/email, repeat and silence (at most seven days). Notifications recheck recipients and have bounded durable retries. BACKUP_AGE also warns when the configured restore-drill interval is overdue.

Only `planner.sweep` and `planner.outbox` accept run/retry/cancel. They dispatch authoritative rechecking workers; direct delivery, financial, erasure and restore replay are excluded. Commands are transactional with pg-boss using its pinned database adapter. A fixed dispatch UUID and Admin receipts prevent duplicate effects. Recheck initiating authority and target state at execution. Cancel only not-yet-active signals; retry at most three extra budgets, up to six retries total. Schedules use UTC minute divisors of sixty between one and fifteen minutes, preserving domain schedules and default minutely recovery. Queue-result retention is configurable by kind and success/failure (7–90 days); bounded terminal expiry never touches domain evidence or pending work.

Storage policy defaults to warning below 1 GiB, with optional immediate block or persisted 1–1,440 minute grace. Actual writes and publication recheck capacity; no quota-driven customer deletion. Cleanup defaults to objects at least 24 hours old (24–720 hours configurable), previews at most 100 orphans/stale temporary objects for fifteen minutes and rechecks references, export/staging identities and file evidence before unlink. Referenced blobs, current attempts, exports and independent control namespaces stay protected. Ordinary lifecycle owners retain disposal authority.

P3 adds only the minimum internal policy/control facilities needed for operations. Four typed policy sections use revision-bound fifteen-minute preview/publish; this does not implement P6 product configuration. Backup schedule defaults off, daily when enabled; drill interval defaults thirty days. PostgreSQL persists manual/scheduled requests and exact P2 retention versions. Requests remain queued until the provisioned operator executes the coordinated backup runbook. API startup never captures/restores data or runs shell/SQL supplied by Admin.

Existing coordinated capture is sealed by the operator with AES-256-GCM, unique nonces and artifact/run-bound authentication, a purpose-separated signed bundle, checksum/decryptability verification and a verified copy to an independently provisioned off-host destination. Encryption keys and target registry stay in protected operator files. The outer bundle shortens expiry to the captured request deadline without rewriting historical signed manifests. Copies and database records alone cannot prove physical failure-domain separation or off-host expiry; those remain deployment gates.

Restore requests name registered opaque targets, expire after thirty minutes and require a different currently authorized Admin. Only an operator console may claim execution; it rechecks approvals and backup validity. Verification targets are isolated databases/file roots using the current independent erasure/shared controls. Never restore old control archives over live controls. Current tombstones, restrictive checkpoint floors, exact migration checksums, all READY bytes/scans, queue/storage/mail and DB readiness must pass before a target may reopen. A one-hour operator lease failing after interruption records failure and never reruns or reopens automatically. Protected signed filesystem status remains readable with API/PostgreSQL offline. Live traffic switching and production restore are outside local acceptance and require separate deployment approval.

No existing recovery deadlines, retention classes, custody mappings, ordinary authentication or Client contracts change. M112 adds eleven control tables and an optional detached audit file target. Twelve FKs reference only Admin/policy/incident/backup state. Fresh-schema and populated P2-to-P3 preservation checks, real PostgreSQL tests and the complete final gate establish local acceptance; operational deployment checks remain explicitly separate.
