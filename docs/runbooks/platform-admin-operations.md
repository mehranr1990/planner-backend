# Platform Admin operational controls

All APIs below use `/api/v1/admin/operations`. See [P3 work record](../platform-admin-p3-work-record.md) for exact permissions, test evidence and acceptance status. Use the separate Admin realm with MFA. Mutations need a trusted Origin, recent persisted MFA, Idempotency-Key and reason. There is no generic shell, SQL, arbitrary-path or privileged content endpoint.

## Health, incidents and safe repair

`GET health` reports live process metrics, PostgreSQL, the stamped queue schema, private-storage capacity, current replay gate, independent maintenance, worker heartbeat and real SMTP connectivity/sink availability. A degraded component is reported as degraded, never fabricated as healthy. Process metrics identify their instance and start time; they do not claim cluster-wide measurements. `POST health/check` authorizes read-only checks. Repair accepts only DISPATCH_SWEEP or RECHECK_DEPENDENCIES. The former dispatches the existing authoritative sweep; neither releases privacy/restore quarantine.

`GET incidents` and permissioned incident notes retain start/recovery and investigation history. Publish HEALTH policy through `policies/preview` then `policies/{id}/publish`. DATABASE/QUEUE/STORAGE/DELIVERY thresholds count unavailable conditions (0 or 1); WORKER uses seconds since last heartbeat; BACKUP_AGE uses hours since a verified unexpired backup and also alerts on an overdue drill; API_ERRORS counts process-local 5xx responses over five minutes. Defaults warn on a 180-second worker gap, 48-hour backup age and 30-day drill interval. Email is delivered through existing SMTP/sink; incident history is the in-app operational channel. Silencing suppresses deliveries, preserves incident history and is bounded to seven days. Notes require their own explicit capability.

## Job controls and retention

`GET jobs` filters all four supported queues and all six pg-boss states. Returned metadata excludes raw payloads, outputs, error messages and credentials. Lists use at most 100 items and an opaque last-ID position. Only sweep/outbox allow run/retry/cancel. The domain workers recheck current permissions, cancellation and idempotency. Do not use these controls to replay individual notifications, erasure, payment or restore effects. Manual retry permits three additional budgets, with a six-retry ceiling; cancellation refuses active jobs. Each control has a durable `job-controls/{id}` status and audit.

Publish JOBS policy after preview. Sweep intervals are UTC minute divisors of sixty from one to fifteen; default one minute. Domain reminder/recurrence schedules do not change. Result policies retain completed/canceled versus failed signals separately by queue (7–90 days). The worker expires at most 100 terminal results per pass through the pinned pg-boss API; domain audit/retention stays independent. Existing pending-dispatch lifetime remains seven days. Policy reconciliation and operational heartbeat run every thirty seconds; no API-startup queue DDL occurs.

## Storage

Usage groups by actual logical scope (falling back to physical Space), MIME type or UTC upload day, with exact-scope and time filters. Overall totals use the same filter and snapshot. At most 100 groups are returned, with explicit truncation; narrow filters for larger inventories. Size totals are decimal strings. This is metadata aggregation, not file-content browsing.

STORAGE policy defaults WARN below 1 GiB free. GRACE persists the first low-capacity instant and blocks after the configured duration; BLOCK refuses new byte uploads and publication immediately. Recovery of capacity clears pressure. Existing files are preserved. Actual storage writes recheck before publication, including Shared/media/export paths.

Cleanup preview retains at most 100 aged candidates for fifteen minutes. Apply requires its fingerprint and rechecks current retention, references, active attempts, export artifacts and exact filesystem size/time. Unknown blobs/stale temporary objects must be at least 24 hours old by default. Customer blobs with metadata remain under their owner module's lifecycle cleanup, even when marked deleted. Never remove files by browsing a volume or overriding references.

Super Admin's explicit private-file capability permits `GET storage/files/{id}/content?spaceId=...&scopeId=...&disposition=attachment`. Shared files require the exact logical scope; Personal files omit it. Optional reason is retained only in restricted audit. A recent persisted MFA check, exact metadata/custody/parent checks and current scan/hash verification precede bytes, and authority is checked while streaming. Only PNG/JPEG may use inline; other types download as opaque bytes. Every access has actor, opaque file target, timestamp and outcome; never log bytes/original filenames. No new file right is inferred for other roles or resources.

## Backup scheduling and operator capture

BACKUP policy controls enabled state, 1–168 hour request interval and 1–90 day drill cadence. Manual `POST backups` and scheduled requests capture the current reviewed P2 BACKUP retention version (1–30 days). A request stays QUEUED until actual capture/sealing; one pending backup is allowed. The schedule is durable and catches up after worker restart without creating an unbounded backlog. Configure a protected operator process to poll approved requests and run the existing coordinated capture. The API never starts a shell or invents a successful backup.

Build the backend before using `pnpm ops:admin` or `tooling/scripts/platform-operations.ts`. Provision operator-only environment:

- `BACKUP_ENCRYPTION_KEY_FILE`: private file with a separately generated 32-byte AES key encoded as base64url; enforce restrictive NTFS/POSIX permissions. Preserve required historical keys outside the database and backup bundle.
- `BACKUP_LOCAL_SEALED_ROOT`: protected local ciphertext staging root.
- `BACKUP_OFFHOST_ROOT`: separately provisioned off-host mounted destination; must not overlap the local sealed root. This path alone does not establish a different failure domain.
- `BACKUP_OFFHOST_APPROVAL`: recorded operational destination approval reference. Verify the destination is outside the server failure domain and test physical expiry before release.
- `OPERATIONS_CONTROL_ROOT`: separately protected persistent directory outside data and erasure/shared control roots. Once configured, missing/corrupt status fails closed. Provision an initial signed READY status only during controlled first setup after readiness/replay verification; never use initialization to clear an active restore.

Run the existing [coordinated backup procedure](backup-restore.md): quiesce API/worker, capture PostgreSQL and file/control artifacts, resume and verify the signed snapshot. A provisioned host operator can poll `pnpm ops:admin backup-next`; it claims one queued request and invokes only the fixed `deploy/backup.sh`, then requires actual VERIFIED evidence. No Admin-supplied command/path reaches the subprocess. Supplying `PLATFORM_BACKUP_REQUEST_ID` to `deploy/backup.sh` invokes sealing after capture. Request IDs make capture directories distinct; existing directories are never overwritten. The ops container needs the protected key file and both provisioned roots mounted by the deployment operator, with consistent protected paths/environment; local P3 does not modify the owner's compose.yaml.

For an existing newly captured artifact directory, the operator may run `pnpm ops:admin backup-seal <request-id> <artifact-directory>`. It validates the signed snapshot, claims the request, encrypts all four fixed artifacts (dump, files, independent-control archive and signed manifest), signs the outer bundle, verifies every decrypted hash, copies only ciphertext to the approved destination and repeats verification there before recording VERIFIED. A filesystem copy does not prove remote failure-domain separation; maintain the independent operational evidence. Retain and expire plaintext/ciphertext staging under the existing protected backup runbook; do not delete the last known good backup automatically.

The outer bundle expires no later than the request's frozen deadline and the original signed manifest. Previously signed manifests, historical policies and tombstones are never rewritten. Physical off-host/staging expiry must be enforced by the provisioned operator process using these signed deadlines, independently of application data restore.

## Controlled restore and drills

Request `POST restores` with backupId, mode DRILL/RESTORE and a registered opaque targetReference. A different Admin reviews that exact backup/target within thirty minutes through `restores/{id}/approve`. Both operators' current eligibility and backup expiry are rechecked when the operator claims. The API cannot claim, report fake completion, supply paths, execute a dump or reopen maintenance.

Provision `RESTORE_TARGET_REGISTRY_FILE` as a protected JSON map from opaque reference to `{ "isolated": true, "environmentFile": "protected-target-config-path" }`. Each target has a distinct isolated database and private-file root, the current independent erasure/shared control roots and required verification keys. Keep operational status independent from restored data; do not reuse the source operational-status directory for an isolated target. Never select the source/live database for verification.

1. Run `pnpm ops:admin restore-claim <request-id>`. It validates the registered isolated target and current two-person review. RESTORE mode writes signed source maintenance status. This command does not restore or overwrite data.
2. Follow the controlled isolated restoration procedure. Authenticate/decrypt the approved bundle, restore only planner.dump and matching business file objects to the empty provisioned target. The encrypted `control.tar.gz` is separately protected recovery material, never an instruction to roll back current erasure/shared controls. Preserve current control-plane approvals/status independently before any separately authorized live transition.
3. Run `pnpm ops:admin restore-verify <request-id>`. It authenticates the registered encrypted backup again, rejects obsolete restrictive floors, runs actual current erasure/shared replay, validates applied migration checksums and every READY file/scan, then checks DB, pinned queue, private-storage and mail readiness. Bounds or missing evidence leave verification incomplete/failed and maintenance closed. A one-hour lease is not automatically renewed or retried.
4. Review the durable VERIFIED drill evidence and independent status. Target reopening requires completed replay/readiness checks. The source remains in maintenance for a separately authorized traffic-switch/recovery action. No timer/countdown, worker restart or failed operator automatically reopens it.

`pnpm ops:admin status` reads signed independent status without connecting to PostgreSQL or booting the API. The trusted local operator may use `pnpm ops:admin emergency-pause <incident-uuid>` to persist fail-closed maintenance while the DB is unavailable; it cannot reopen access. These commands require the separately protected operator configuration/signing keys. A configured unavailable/corrupt status produces failure, not READY. API Admin routes remain available through the ordinary Admin security realm when the DB is available; no alternate unauthenticated control route exists.

Actual encrypted off-host storage, physical expiry, Docker capture/restore, full operational RPO/RTO and live scanner evidence are deployment checks. Local encryption/integration tests are explicitly synthetic fixtures and do not claim production backup or restore readiness.
